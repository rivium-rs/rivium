# Architecture

Rivium is the part of a long-running service that every service needs and that is easy to get
wrong: the service lifecycle (start, readiness, a stop with a deadline, restarts, exit codes),
configuration loading, logging within a disk budget, and the hosts that run the services, as a
program of their own or inside an Android app. A service depends on it as versioned crates, so
a fix to that part reaches every service through `cargo update`, a rebuild and a redeploy,
instead of an edit in every copy.

## What goes where

| Part | What it holds | How it changes |
| --- | --- | --- |
| Library crates (crates.io) | What is the same in every service and costly to get wrong: lifecycle, signals and exit codes, FFI, the log budget, the error model | Released together at one version; consumers take fixes with `cargo update` |
| The template | What every service needs but tailors: the workspace layout, the composition root, configuration files, packaging for each platform, CI, checks, AGENTS.md | Generated once and then owned by the service; `just template-diff` shows later changes to merge by hand |
| Examples (`examples/`) | How to use the crates, and what the tests and drills run against | Not published |
| The service | Its business: domain logic, configuration schema, adapters, protocol bindings such as the HTTP endpoints of log export | Its own |

A piece of code belongs in the library when a defect in it should be fixed once for every
service. Rivium has no plugin system, dependency-injection container, macro DSL or choice of
async runtime: tokio is the runtime, and a host runs one.

## Crates

| Crate | What it is | Depends on |
| --- | --- | --- |
| `rivium-error` | The error type: a kind (a stable name and a class), the party responsible, a retry hint, context and a cause chain, and their log fields | `tracing` only |
| `rivium` | The service model and lifecycle, the process and embedded hosts, configuration, logging and log export | `rivium-error`, tokio, tracing, serde; no C code |
| `rivium-http` | An HTTP server service on axum: the status envelope, request ids, the access log, probes | `rivium`, axum |
| `rivium-jni` | The JNI library of the embedded host, generated by one macro | `rivium`, jni |
| `rivium-test` | Test support: scripted services, log capture, process tools, contract suites, dependency checks | `rivium`; a dev-dependency only |

```text
rivium-error <── rivium <── rivium-http
                    ^  <─── rivium-jni
                    └────── rivium-test (dev-dependency)

service library ──> rivium (and rivium-http when it serves HTTP)
program         ──> service library, rivium
JNI library     ──> service library, rivium-jni
```

`rivium` never depends on the HTTP or JNI crates, and the HTTP and JNI crates never depend on
each other, so a service compiles only what it uses: a service without HTTP has no axum or hyper
in its build, and its program has no JNI. The tests check these closures for the platform they
run on (`rivium_test::deps::assert_closure_excludes`). The only feature is `log-export` of
`rivium`, which adds log export and the `zip` crate; features are additive.

## A service

A service program is a composition root, an implementation of `rivium::App`, in its service
library: its name and version, its configuration type, and `services()`, which builds the
services from the configuration without starting them.

```rust
impl rivium::App for Agent {
    const NAME: &'static str = "agent";
    const VERSION: &'static str = env!("CARGO_PKG_VERSION");
    type Config = Config;

    fn services(config: &Config, ctx: &rivium::AppContext) -> rivium::Result<Vec<Box<dyn rivium::Service>>> {
        Ok(vec![
            Box::new(UdpAgent::new(&config.agent, ctx.health())),            // frontline
            rivium::periodic("poller", config.poll.every, poller::tick(&config.poll)),
        ])
    }
}
```

The program's `main` is `rivium::process::run::<Agent>()`; a JNI library is
`rivium_jni::export!(class = "com/example/agent/RiviumBridge", app = Agent);`. Both run the same
composition root, and adding a service, a configuration section or another program changes only
the service's own code.

| Concept | Rule |
| --- | --- |
| Service | A `Service`, or one built with `rivium::service(name, kind, |ctx| async { .. })` or `rivium::periodic(name, every, tick)` |
| Frontline, background | Frontline services take outside traffic and stop first; returning before they are asked to stop is a failure. Background services stop after them and may finish early |
| Ready | `ctx.ready()` once the service takes traffic. The run is running once every service is ready, and ready once, besides, every registered health item is healthy |
| Tasks | `ctx.spawn` and `ctx.spawn_blocking` start tasks that belong to the service: they get its stop request and deadline, and their first failure is the service's |
| Stopping | `ctx.stopped()` completes when it is the service's turn to stop; `ctx.deadline()` says when it must be done. A blocking task checks `is_stopping()` between calls, each shorter than the stop budget |
| Restart | `ctx.restarter().request(reason)` stops the run gracefully for a restart, for example once a new configuration is written |
| New configuration | Whatever takes one, such as a request handler, keeps a clone of the `AppContext`: `ctx.check_config(text)` checks it as the next start would load it, `rivium::fs::atomic_write(ctx.paths().config_file(), ..)` writes it, and a restart request loads it |

## The lifecycle

A supervisor runs the services of a run through four phases: starting, running, stopping and
stopped. It is a pure state machine fed by one ordered channel, so its outcome depends on the
order of events only, never on scheduling.

- **Starting**: every service must be ready within `lifecycle.startup_timeout` (30 s). A service
  that fails before it is ready fails the startup.
- **Running**: a service that fails is a fault, and the run stops.
- **Stopping**: on a stop request, a fault or a restart request, the frontline services are
  asked to stop, then the background ones, all within one deadline, `lifecycle.stop_timeout`
  (3 s). Services still running at the deadline are abandoned and named.
- The first cause of a stop is the one reported: a later failure is logged as secondary, except
  that a failure while stopping on request turns the stop into a fault. An outside stop wins
  over a restart request. A second outside stop cuts the stop short.

After the deadline the host needs at most one more second: 400 ms for the runtime to shut down,
100 ms to cancel a log export, 500 ms to flush the logs. The default stop budget, 4 s, is below
the shortest time that a supervisor waits before it kills a service (about 5 s for a macOS
LaunchAgent, 15 s for WinSW, 90 s for systemd); a host logs a warning when a configured budget
exceeds the platform's.

## The hosts

### A program of its own

`rivium::process::run` parses a small command line, finds the root directory, loads the
configuration, installs logging, builds a tokio runtime and runs rounds of services until it is
stopped.

```text
<program> [run] [--root DIR | WorkDir=DIR] [--config FILE] [--set KEY=VALUE]...
<program> check-config [--root DIR | WorkDir=DIR] [--config FILE] [--set KEY=VALUE]...
<program> default-config [--set KEY=VALUE]...
<program> --version | --help
```

Without arguments the program runs. SIGTERM and SIGINT stop it, and on Windows CTRL_C and
CTRL_BREAK (as SIGINT) and CTRL_CLOSE, CTRL_LOGOFF and CTRL_SHUTDOWN (as SIGTERM). A program
never daemonizes, writes a PID file or calls `process::exit`. With `lifecycle.restart = "exit"`
(the default) a restart request exits with 75 for the supervisor to restart the program; with
`"in-process"` the program rebuilds its services itself, backing off after failures, for
deployments whose supervisor does not restart.

### Embedded

`rivium::embedded::Host` runs the same composition root inside another program, such as an
Android app through `rivium-jni`: `start(args)` runs the services on a thread of its own and
returns the outcome of the first round, `stop(timeout)` stops them within the timeout,
`status()` and `last_error()` describe the host. Start and stop can be repeated in one process;
failures after the first round restart the services in the process. An embedded host reads no
environment variables and installs no signal handlers.

### Exit codes and result codes

| Code | Exit code | JNI result | When |
| --- | --- | --- | --- |
| Ok | 0 | 0 | Stopped as asked; `--version`, `--help`, a valid `check-config` |
| AlreadyRunning, NotRunning, Busy, Cancelled | — | 1, 2, 3, 4 | A start while running, a stop while idle, a start while stopping, a start cancelled by a stop |
| Usage | 64 | −64 | Invalid arguments |
| StartupFailed | 69 | −69 | The services did not start (including a panic while building them) |
| Fault | 70 | — | A service failed while running |
| OsError | 71 | −71 | No runtime, thread or signal handler |
| CantCreate | 73 | −73 | The log directory cannot be written |
| Restart | 75 | — | A restart was requested |
| Config | 78 | −78 | An invalid configuration, one line per problem on stderr |
| StopTimedOut | 124 | −124 | Services were abandoned at the deadline |
| Aborted | 130, 143 | — | A second stop signal |
| Panicked | — | −99 | A panic in a JNI entry point |

Every profile keeps `panic = "unwind"`: a panic in a service is a failure of that service, and
`rivium-jni` refuses to build with `panic = "abort"`.

## Configuration

A service's configuration is plain serde types, its sections at the top level of a TOML file;
`log` and `lifecycle` are Rivium's sections. Values come from, in rising precedence: the
defaults, the file, environment variables (`<PREFIX>_<SECTION>__<KEY>`, where the prefix is the
service's name in upper snake case; `RUST_LOG` for `log.filter`), and `--set section.key=value`.
`Option` fields and maps work from every source. Every problem is reported at once, one line
each with the key and its source, and unknown keys are problems. `check-config` lists every key
with its value and source; `default-config` prints the defaults, which the template keeps in
`configs/default.toml`.

The root directory is `--root` (or `WorkDir=`), else `<PREFIX>_ROOT`, else the program's
directory; paths in the configuration are relative to it. The configuration file is `--config`,
else `<PREFIX>_CONFIG`, else the service's file below the root. A host never changes the working
directory.

## Logging

| Output | Where |
| --- | --- |
| Console | A program's standard output: the log filter when it is a terminal, warnings and errors otherwise; text or JSON. Text is colored on a terminal unless `NO_COLOR` is set or `TERM` is `dumb`; `log.console.color` (`auto`, `always`, `never`) overrides it |
| Main file | `logs/<name>/<name>.log` below the root |
| Category files | `[[log.files]]` with a name and a filter of their own |
| logcat | Android, embedded |
| More layers | `App::log_layers`, for example a bridge to a telemetry system |

Files roll by size and by day and are compressed in the background. The directory has a budget,
`log.file.max_total_size`: the oldest files are deleted by their sequence number, never by a
clock that a device may not have, and the directory never exceeds its budget by more than one
file per output. Before a stop returns, a flush barrier puts every event in its file. With the
feature `log-export`, `ctx.log_exporter()` packs the log files of chosen days into a zip archive
to download; the service binds it to its own protocol.

## Errors and HTTP

An error kind is a constant: `const DEVICE: ErrorType = &ErrorKind::new("DeviceError",
Class::Unavailable);`. Its class decides the HTTP status when `rivium-http` answers with it:

| Class | Status |
| --- | --- |
| InvalidInput, InvalidBody | 400, 406 |
| Unauthenticated, Forbidden | 401, 403 |
| NotFound, Conflict, TooManyRequests | 404, 409, 429 |
| Unavailable, Timeout, Internal | 503, 504, 500 |

An error that the service's dependencies caused (`into_up()`) is never the caller's fault: a
4xx class becomes 500 (503 for TooManyRequests). Every answer carries `x-request-id`; failures
and `ApiResponse::Ok` use the envelope `{"status":…,"code":…,"description":…}`, data is plain
JSON. A server error's description is a fixed phrase with the request id; the error itself goes
to the log, once. `HttpServer` also serves `/livez` and `/readyz`.

## Testing a service

`rivium-test` brings what a service's own tests need:

- `process::lifecycle_contract(bin, args)` and `embedded::lifecycle_contract::<App>(root, args)`:
  the contract every program built on Rivium keeps (version, an invalid configuration, a
  side-effect-free `check-config`, a stop within the default budget, a second stop; repeated
  starts and stops when embedded). `args` set what the defaults need in a test, such as a free
  port in place of the deployment's.
- `process::spawn`: a program started as a supervisor would, with its events readable.
- `ScriptedService` and `capture_logs` for tests of the lifecycle itself.
- `deps::assert_closure_excludes`: the dependency closure of a package has none of the given
  crates.

## How it is verified

[platforms.md](platforms.md) lists each target, how far it is verified and by which CI job.
Besides the tests on every target, CI runs:

- **The template** (`ci/template`): projects generated with and without HTTP and JNI, checked as
  their own CI would, with planted violations of their rules.
- **Scenario A** (`ci/drills`): a planted shutdown defect in one release fails the lifecycle
  contract tests of a program and an embedded consumer; the next release fixes it, and the
  consumers pass after `cargo update`, with only their `Cargo.lock` changed.
- **Scenario C** (`ci/drills`): a new background service, program and configuration section
  change only the service's code.
- **Hosting** (`hosting/*`): the `udp-echo` example under systemd, launchd and WinSW, stopped as
  those supervisors stop it, and restarted after a restart request.
